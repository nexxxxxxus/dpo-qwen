# Как разворачивали Qwen3-8B на сервере с A100

Отчёт о настройке проекта `dpo-qwen` 4 октября 2026 года: что делали, какие проблемы возникли, как их решили и какие были альтернативы. Итог — модель `Qwen/Qwen3-8B` запускается через vLLM на GPU сервера и отвечает на запросы.

## Исходные условия

- **Mac** — рабочее место: здесь пишется код. GPU нет.
- **Сервер** — 8× NVIDIA A100 80GB, Ubuntu 22.04, драйвер NVIDIA 570.86 (поддерживает CUDA до 12.8), доступ по `ssh a100`. Сервер общий, прав sudo нет.
- **Код** переносится только через git: `push` с Mac, `pull` на сервере.
- **Тяжёлые файлы** (веса, датасеты, результаты) живут только на сервере.

## Итоговая конфигурация

| Что | Значение |
|---|---|
| Код | `~/dpo-qwen` на Mac и на сервере, ветка `main` |
| Данные (`DATA_DIR`) | `/home/nsibgatullin/data/dpo-qwen` с папками `models`, `data`, `outputs`, `hf_cache` |
| Модель | `Qwen/Qwen3-8B`, 16 ГБ, общая копия в `/data/shared/dpo_team/models/Qwen3-8B` |
| Окружение | conda, Python 3.12.14, в `~/dpo-qwen/.venv` |
| Ключевые пакеты | `vllm 0.30.0+cu129`, `torch 2.13.0+cu129`, `trl 1.14.1` |
| Запуск на GPU | только через Slurm: `sbatch` или `srun --gres=gpu:N` |
| Запуск скриптов | через обёртку `scripts/run.sh` |

## Этап 1. Клон репозитория на Mac

Адрес репозитория взяли с сервера (`git remote get-url origin`) и клонировали в `~/dpo-qwen`.

**Проблема.** Клонирование упало с ошибкой `Host key verification failed`: в `~/.ssh/known_hosts` на Mac не было записи о GitHub.

**Решение.** Ключ GitHub получили через `ssh-keyscan`, сверили его отпечаток (`SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU`) с официально опубликованным и только после совпадения добавили в `known_hosts`.

**Альтернативы.** Опция `StrictHostKeyChecking=accept-new` принимает любой ключ без проверки. Клон по HTTPS требует токена и расходится с SSH-схемой, которая уже работает на сервере.

## Этап 2. Папка для данных

Общей папки `/data/dpo-qwen` не существовало, а `/data` принадлежит root, поэтому данные разместили в домашней папке: `~/data/dpo-qwen`. Позже админ подтвердил, что своё нужно хранить именно в домашней папке.

В `~/.bashrc` на сервере уже была админская строка `export HF_HOME=$HOME/hf`. Её не стали править, а дописали в конец файла свои строки:

```bash
umask 002
export HF_HOME=$HOME/data/dpo-qwen/hf_cache
```

Более поздняя строка переопределяет раннюю, а админский блок остаётся нетронутым. Hugging Face с сервера доступен напрямую, зеркало не понадобилось.

## Этап 3. Выбор модели

Нужна была модель размером около 8B. У Qwen2.5 такого размера нет (ближайший — 7B), поэтому взяли `Qwen/Qwen3-8B`.

У Qwen3 по умолчанию включён режим размышлений: перед ответом модель пишет блок `<think>…</think>`. Для генерации пар chosen/rejected он мешает, поэтому в коде его отключают через `chat_template_kwargs={"enable_thinking": False}`.

**Альтернативы.** `Qwen/Qwen2.5-7B-Instruct` — без режима размышлений, но меньше и старше. `meta-llama/Llama-3.1-8B-Instruct` — закрытая модель, нужен токен и принятие лицензии.

## Этап 4. Окружение Python

**Проблема 1.** Команда `python3 -m venv` не работает: у системного Python 3.10 нет пакета `python3-venv`, а его установка требует sudo. Python из conda на сервере имеет версию 3.14, слишком новую для vLLM.

**Решение.** Создали conda-окружение с Python 3.12 прямо в `~/dpo-qwen/.venv`. Пути вида `.venv/bin/python` остались такими же, как у обычного venv.

**Альтернативы.** Поставить `virtualenv` в домашнюю папку и собрать окружение на системном Python 3.10 — работает, но требует лишнего обходного шага. Ждать, пока админ поставит `python3-venv`.

**Проблема 2.** `conda create` упал с ошибкой `CondaToSNonInteractiveError`: каналы Anaconda по умолчанию требуют принять условия использования.

**Решение.** Тот же Python 3.12 взяли из открытого канала conda-forge, где условий принимать не нужно:

```bash
/opt/conda/bin/conda create -y -p .venv --override-channels -c conda-forge python=3.12
```

**Альтернатива.** Принять условия Anaconda командой `conda tos accept`. Это юридическое согласие, и давать его должен сам пользователь.

## Этап 5. Скачивание модели

Модель скачали в tmux-сессии, чтобы обрыв SSH не прервал загрузку:

```bash
HF_HOME=<DATA_DIR>/hf_cache .venv/bin/hf download Qwen/Qwen3-8B \
  --local-dir <DATA_DIR>/models/Qwen3-8B
```

Получилось 16 ГБ: `config.json`, токенизатор и пять файлов `safetensors`.

## Этап 6. Тестовый запуск vLLM

Тестовый скрипт `scripts/smoke_test.py` читает путь к модели из `configs/model.yaml`, поднимает движок vLLM и генерирует два ответа на один вопрос. До успеха потребовалось шесть попыток.

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 1 | `CXXABI_1.3.15 not found` при импорте | Подхватывалась старая системная `libstdc++` | Обёртка `scripts/run.sh` |
| 2 | `NVIDIA driver too old (found 12080)` | Пакеты собраны под CUDA 13, драйвер — CUDA 12.8 | Сборки `+cu129` |
| 3 | `libnvrtc.so.13: cannot open` | `torchcodec` тоже под CUDA 13 | `torchcodec==0.16.0+cu129` |
| 4 | Движок молча умирает | Сторожевой скрипт убивает GPU-процессы вне Slurm | Запуск через `sbatch` |
| 5 | `Could not find nvcc` | FlashInfer компилирует ядра на лету, компилятора нет | `flashinfer-jit-cache` |
| 6 | Успех | — | — |

### Попытка 1. Системная libstdc++

Python из conda-forge приносит свою, более новую библиотеку `libstdc++`. Но PyTorch первым загружал системную, более старую, и следующий модуль (`sqlite3`) уже не находил в ней нужных символов.

**Решение.** Обёртка `scripts/run.sh` задаёт `LD_LIBRARY_PATH=<репозиторий>/.venv/lib` и запускает Python из окружения. Все скрипты проекта запускаются через неё.

**Альтернативы.** Экспортировать `LD_LIBRARY_PATH` в `~/.bashrc` — тогда системные программы (git, ssh) тоже начали бы грузить библиотеки conda, что может их сломать. Импортировать `sqlite3` раньше PyTorch в каждом скрипте — хрупко.

### Попытка 2. Версия CUDA

vLLM 0.30.0 и PyTorch 2.13 из PyPI собраны под CUDA 13. Драйвер сервера (570.86) поддерживает только CUDA 12.x, поэтому PyTorch отказался инициализировать карту.

Что выяснили:

- Сборок PyTorch под CUDA 12.8 для версии 2.13 нет, они заканчиваются на 2.11.
- vLLM начиная с 0.27 требует PyTorch 2.13.
- У vLLM 0.30.0 есть официальная сборка под CUDA 12.9 (`+cu129`), и для неё есть PyTorch 2.13 той же сборки.
- Внутри одной основной версии CUDA более новая библиотека работает на более старом драйвере, поэтому сборка 12.9 запускается на драйвере 12.8.

**Решение.** В `requirements.txt` закрепили сборки `+cu129` и добавили адреса индексов, откуда они ставятся. Окружение удалили и создали заново, чтобы в нём не осталось пакетов от CUDA 13.

```
--extra-index-url https://wheels.vllm.ai/0.30.0/cu129
--extra-index-url https://download.pytorch.org/whl/cu129
vllm==0.30.0+cu129
torch==2.13.0+cu129
torchvision==0.28.0+cu129
torchaudio==2.11.0+cu129
```

**Альтернативы.** Откатить vLLM до 0.26 — не помогло бы, его сборка по умолчанию тоже под CUDA 13. Обновить драйвер — нужен sudo, и это затронуло бы всех пользователей сервера.

### Попытка 3. torchcodec

После пересборки один пакет, `torchcodec`, всё равно пришёл из PyPI в сборке под CUDA 13 и искал библиотеку `libnvrtc.so.13`.

**Решение.** Поставили `torchcodec==0.16.0+cu129` и закрепили в `requirements.txt`. Это последняя версия, для которой есть сборка под CUDA 12.9; vLLM требует не ниже 0.14.

### Попытка 4. Молчаливая смерть движка

Модель загрузилась на карту за 5 секунд, но через 20–30 секунд процесс движка исчез без какой-либо ошибки в логе. vLLM сообщал только `Engine core initialization failed. Failed core proc(s): {}`.

Как искали причину:

1. Диагностический скрипт показал код завершения −9, то есть процесс получил SIGKILL.
2. Нехватку памяти исключили: лимитов для пользователя нет, счётчик убийств по памяти нулевой, свободно 1.7 ТБ.
3. Вторая диагностика показала, что процесс был мёртв ещё до того, как vLLM начал его останавливать. Значит, убивал кто-то снаружи.
4. В cron нашёлся скрипт `/usr/local/sbin/gpu_guard.sh`. Раз в минуту он убивает любой процесс на GPU, запущенный не из задачи Slurm.

**Решение.** Запускать через планировщик Slurm:

```bash
sbatch --gres=gpu:1 --cpus-per-task=8 --mem=64G -t 0:20:00 \
  -J nadir-smoke -o <DATA_DIR>/outputs/smoke.log \
  --wrap "cd ~/dpo-qwen && scripts/run.sh scripts/smoke_test.py"
```

Карту выбирает сам Slurm, переменную `CUDA_VISIBLE_DEVICES` вручную задавать не нужно. Задача переживает обрыв SSH, tmux для неё не нужен.

**Альтернативы.** Их нет: это правило сервера. Запуск из tmux с `CUDA_VISIBLE_DEVICES` здесь не работает.

### Попытка 5. Компилятор nvcc

Через Slurm движок дошёл до первого запроса и упал на сэмплировании. Библиотека FlashInfer, которую vLLM использует для top-p и top-k, компилирует свои ядра при первом вызове, а компилятора CUDA (`nvcc`) на сервере нет.

**Решение.** Поставили пакет с предсобранными ядрами, версия которого точно совпадает с версией FlashInfer:

```
--extra-index-url https://flashinfer.ai/whl/cu129
flashinfer-jit-cache==0.6.18.post1+cu129
```

**Альтернативы.** Отключить сэмплер FlashInfer переменной `VLLM_USE_FLASHINFER_SAMPLER=0` — работает, но сэмплирование медленнее. Поставить `nvcc` через conda — тяжелее и требует ещё и заголовков CUDA.

### Попытка 6. Успех

Задача Slurm завершилась с кодом 0. В логе два разных осмысленных ответа, без ошибок и без блока `<think>`:

```
QUESTION: Объясни в двух-трёх предложениях, почему небо голубое.

=== ANSWER 1 ===
Небо голубое из-за того, что молекулы атмосферного воздуха рассеивают солнечный свет, особенно в синей части спектра. Этот эффект называется рассеянием Рэлея, и он делает небо кажущимся голубым в ясный день.

=== ANSWER 2 ===
Небо голубое из-за того, что молекулы воздуха рассеивают солнечный свет, особенно синий и фиолетовый, и мы видим голубой цвет, потому что синий свет рассеивается сильнее и попадает в наше глазное яблоко.
```

## Правила сервера, которые выяснились по ходу

- **GPU только через Slurm.** Процесс на карте вне Slurm убивается в течение минуты.
- **Лимит времени.** По умолчанию задача живёт 8 часов, максимум — 2 суток (`-t 2-00:00:00`).
- **Простой.** Задачу, у которой карта около двух часов загружена меньше чем на 5%, система отменяет.
- **Данные.** Своё хранится в домашней папке, она видна только владельцу. `/data/shared` — общие модели и датасеты только для чтения, их наполняют менторы.
- **Полезные команды.** `squeue` — очередь, `scancel <номер>` — снять задачу, `sinfo` — состояние карт.

## Что осталось непроверенным

- **`requirements.lock.txt`.** Снят с рабочего окружения, но установка с нуля по нему не проводилась.
- **Запуск под другим логином.** Модель сначала скачали в `~/data/dpo-qwen/models/Qwen3-8B`, позже ментор положил общую копию в `/data/shared/dpo_team/models/Qwen3-8B` (контрольные суммы совпадают с исходной), и `configs/model.yaml` указывает на неё. Запуск под логином другого участника не проверялся.
