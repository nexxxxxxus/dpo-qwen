# dpo-qwen

Дообучение Qwen методом DPO: генерируем ответы модели через vLLM, размечаем пары chosen/rejected и обучаем модель через DPO (библиотека TRL).

## Схема работы

```
Mac (код)  →  git push  →  GitHub  →  git pull  →  сервер (GPU, данные, запуски)
```

- **Код** пишем на своих машинах и переносим на сервер только через git. Через scp код не копируем.
- **Сервер** — 8× NVIDIA A100 80GB, Ubuntu 22.04. Код лежит в `~/dpo-qwen`.
- **Тяжёлые файлы** (веса, датасеты, результаты) живут только на сервере в `DATA_DIR` и никогда не попадают в git.

`DATA_DIR` — это `~/data/dpo-qwen` в домашней папке каждого участника. По правилам сервера своё хранится в домашней папке, и она видна только владельцу, поэтому датасеты, результаты и чекпойнты у каждого свои. Базовая модель общая: `/data/shared/dpo_team/models/Qwen3-8B` (только чтение, её положил ментор), скачивать её себе не нужно.

```
DATA_DIR/
├── models/     веса моделей
├── data/       датасеты
├── outputs/    результаты запусков
└── hf_cache/   кэш Hugging Face (HF_HOME)
```

## Окружение на сервере

У системного Python на сервере нет модуля `venv`, поэтому окружение создаётся через conda (Python 3.12) в папке `.venv` внутри репозитория:

```bash
cd ~/dpo-qwen
/opt/conda/bin/conda create -y -p .venv --override-channels -c conda-forge python=3.12
.venv/bin/pip install -U pip
.venv/bin/pip install -r requirements.lock.txt
```

Канал `conda-forge` указан явно: каналы Anaconda по умолчанию требуют принять условия использования, а `conda-forge` — нет.

Версии vLLM и PyTorch в `requirements.txt` закреплены в сборке под CUDA 12.9: драйвер сервера поддерживает только CUDA 12.x, а сборки по умолчанию из PyPI рассчитаны на CUDA 13 и на сервере не запускаются.

`requirements.txt` — список зависимостей, `requirements.lock.txt` — точные версии, с которыми всё проверено.

В `~/.bashrc` на сервере должны быть строки:

```bash
umask 002
export HF_HOME=$HOME/data/dpo-qwen/hf_cache
```

Строки дописываем в конец файла, после админской `export HF_HOME=$HOME/hf`: более поздняя строка её переопределяет.

## Запуск на GPU

GPU на сервере выдаёт только планировщик Slurm. Процесс, занявший карту в обход Slurm (например, из tmux с `CUDA_VISIBLE_DEVICES`), в течение минуты убивает системный скрипт `gpu_guard`.

Скрипты запускаем через обёртку `scripts/run.sh`, а не напрямую через `.venv/bin/python`: она подставляет библиотеки окружения, без которых импорт vLLM падает с ошибкой `CXXABI_1.3.15 not found`.

Фоновая задача (переживает обрыв SSH, tmux не нужен):

```bash
cd ~/dpo-qwen
sbatch --gres=gpu:1 --cpus-per-task=8 --mem=64G -t 2:00:00 \
  -J <имя>-<задача> -o <DATA_DIR>/outputs/<папка запуска>/log.txt \
  --wrap "cd ~/dpo-qwen && scripts/run.sh scripts/smoke_test.py"
```

Интерактивная сессия с картой: `srun --gres=gpu:1 --cpus-per-task=8 --mem=64G -t 2:00:00 --pty bash`.

- Очередь и свои задачи: `squeue`, отмена: `scancel <номер>`.
- Карту выбирает Slurm, `CUDA_VISIBLE_DEVICES` вручную не задаём. Для нескольких карт — `--gres=gpu:N`.
- Без `-t` задача живёт 8 часов, максимум — 2 суток (`-t 2-00:00:00`). Задачу, у которой карта около двух часов загружена меньше чем на 5%, система отменяет сама.

## Структура репозитория

- `configs/` — конфиги; `configs/model.yaml` хранит путь к модели на сервере (общая копия в `/data/shared`)
- `scripts/` — запускаемые скрипты
- `src/` — код проекта

## Правила для команды

- **Ветки.** Каждый работает в своей ветке и вливает её в `main` через Pull Request. В `main` попадает только проверенное.
- **GPU.** Сервер общий. Карты берём только через Slurm (`sbatch` / `srun --gres=gpu:N`) и не больше, чем нужно. Чужие задачи и процессы не трогаем.
- **Имена.** Задачи Slurm и tmux-сессии называем `<имя>-<задача>`, например `nadir-generate`. tmux используем для долгих команд без GPU (скачивание, установка).
- **Результаты.** Каждый запуск пишет в `<DATA_DIR>/outputs/<дата>-<имя>-<что>/`, например `2026-10-04-nadir-generate/`, и кладёт туда копию конфига, с которым запускался.

## Раскладка моделей по картам

На A100 80GB: до 14B — одна карта на копию модели; 32B — `tensor_parallel_size=2`; 72B — `tensor_parallel_size=4`.
